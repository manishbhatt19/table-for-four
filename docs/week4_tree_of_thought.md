# Table for Four — Tree of Thought: A Design Decision

**Author:** Manish Bhatt

> Week 4 asks whether **Tree of Thought (ToT)** reasoning belongs in the capstone. It
> does not, and this document is the argument for that — not a shrug at it. Section 2
> works out what a ToT implementation would concretely have looked like in this
> architecture, section 3 shows why each part of it loses to what is already built, and

> Sections 5–7 state the reasoning approach that does fit and the conditions under which

## 1. Verdict

**ToT reasoning is not appropriate for Table for Four, and adopting it would actively
hinder the design.**

Three sentences, then the detail. The alternatives this agent must weigh are *retrieved
from the world*, not generated by the model, so the tree's breadth would be manufactured
rather than real. The selection among those alternatives is *deliberately the guest's*,
so an internal search that returns one answer would delete the product's core promise.
And the constraints that matter are *checked by tool calls with exact answers*, so a
scored critic would be a weaker instrument than the function it replaced.

## 2. What ToT would have looked like here

Stating the mechanics concretely, because rejecting a technique in the abstract is not a
design decision.

Mapping the ToT vocabulary onto this system, the honest reading is:

| ToT concept | Nearest thing in Table for Four |
|---|---|
| **Thought** | One candidate outing: a (restaurant, date, time, party size, perk) tuple, partially filled |
| **Node** | The state of that partial outing after one more constraint is resolved |
| **Branch** | An alternative resolution — a different restaurant, a different time slot, or a different constraint relaxed |
| **Depth** | Constraint-resolution stages: cuisine/area → restaurant → time → confirmation |
| **Branching factor** | ~4 restaurants (`MAX_RECOMMENDATIONS = 4`, `concierge_chat.py:64`), ~3–6 open times per restaurant |
| **Depth limit** | 3–4, since the outing is fully specified by then |
| **Termination** | A complete tuple that passes availability and gets guest approval |

So the tree is not hard to imagine — it is roughly breadth 4, depth 3. That is precisely
what makes the rejection interesting: the tree is *already there*. The question is not
whether this problem has a search structure. It is **who runs the search**, and what the
evaluator is made of.

## 3. Why ToT loses on this problem

### 3.1 The branches are retrieved, not reasoned

ToT earns its cost when the solution space must be *invented* by the model — proofs,
puzzles, program synthesis, creative planning — and where the model can generate a
genuinely novel next step that no external system could hand it.

Here the candidate set comes from the Google Places API through the search MCP server,
filtered by cuisine, area, price, and rating. The model does not think its way to a
fifth restaurant; it fetches one. Asking an LLM to expand branches over a retrieved
candidate list adds a generation step whose output is bounded by data it was already
given. That is not reasoning — it is re-typing the list.

### 3.2 The human is the search algorithm, by design

This is the decisive one.

The product premise, stated in the scoping doc and enforced in code, is that the guest
chooses. The concierge presents a shortlist and the guest picks the restaurant. The
concierge presents open times and the guest picks the time. The concierge reads the
booking back and waits for a yes (`concierge_chat.py`, journey step 6). Standing
preferences — home area, usual party size, favourite cuisines — cannot be changed
without the guest's explicit agreement (`sticky_conflicts` in `profile_memory.py`,
shipped in `ab5008e`).

**The tree already runs. Breadth 4, depth 3, and the guest is the critic.**

ToT is a technique for the model to explore alternatives *instead of* asking. Internalizing
this search would mean evaluating four restaurants against an invented rubric, pruning
three, and presenting the survivor as though it were the answer. For a hospitality
product whose whole differentiator is "ask, never assume," that is not a neutral
architectural choice — it is the failure mode the system was built to prevent. The
consent gate would sit alongside a search procedure designed to make the same class of
unilateral judgement it exists to forbid.

### 3.3 There is no trustworthy online evaluation signal

ToT requires a state evaluator good enough that pruning on its score is better than not
pruning. Ask what the critic would actually score here: *is Osteria a better dinner than
Kiki's?* There is no ground truth. Rating and price level are already retrieved and
already shown to the guest. Everything beyond them — occasion fit, atmosphere, whether
this particular birthday wants noise or quiet — is exactly the knowledge the guest has
and the model does not.

Where this project *can* measure retrieval quality, it does so properly and offline:
`mcp_servers/perks/eval.py` scores the perks retriever against a labeled benchmark with
`hit@k`, `prec@k`, and MRR, deterministically and reproducibly. That is the right shape
for an evaluation signal — fixed labels, standard IR metrics, runs in CI.

An online LLM critic scoring restaurant desirability would have none of those properties.
The assignment lists "weak evaluation signals leading to pruning the best branch" as a
*risk to mitigate*. Here it is not a risk to be mitigated; it is disqualifying, because
the pruned branches are real restaurants the guest never gets to see, discarded on a
score with nothing behind it.

### 3.4 The constraints are checked, not evaluated

The hard constraints in this domain all have exact answers from tool calls: is the table
available at 19:00 (`check_availability`), does the party size fit, is the booking more
than 24 hours out (`CANCELLATION_WINDOW_HOURS`), is an email on file before booking, does
this perk apply on a Friday for four people (perks server metadata filters).

None of these benefits from a scored branch. A constraint with a deterministic checker
should be checked, not estimated — the check is cheaper, exact, auditable, and it cannot
hallucinate. ToT's constraint-complexity argument applies where satisfaction is expensive
to test or must be judged; here it is a function call.

### 3.5 Cost and latency, against a live conversational demo

A guest turn currently costs between 1 and 7 model calls (`MAX_TOOL_HOPS = 6`, plus the
final reply, `concierge_chat.py:63`). A modest ToT pass at breadth 3, depth 3 adds on the
order of a dozen generations plus a dozen evaluations *per decision point*. In a chat UI
being screen-recorded for the capstone demo, that is a visible stall in the middle of a
conversation, paid for on every outing, to reach a restaurant the guest was going to be
shown anyway.

## 4. The strongest candidate site — and why it still loses

Steelmanning honestly: the one place in this architecture with a genuine search
structure is **constraint relaxation after an empty search**. "Vegan, gluten-free
option, high chair, Friday 19:00, Midtown, under $$, must carry a perk" can return
nothing, and something has to give. Which constraint to relax is a real branching
decision with real consequences.

That is `refine_node` in `graph.py:76`, and it is already solved — with a fixed
domain-ordered relaxation ladder:

```
min_rating  →  raise price ceiling  →  drop open-now  →  drop cuisine filter
```

bounded by `MAX_ITERATIONS = 2` and routed by a conditional edge (`route_after_search`,
`graph.py:99`).

Why the ladder beats a tree here:

- **The evaluator is a tool call, not a critic.** "Did the search return candidates?" is
  answered exactly by the search itself. Tree search buys you the ability to compare
  branches under uncertainty — there is no uncertainty to price.
- **The branching factor is ~4 with an obvious domain priority.** A guest would rather
  eat at a 4.1-star restaurant than eat nothing; they would rather pay one price band
  more than abandon dinner; they would rather change cuisine than change nothing. That
  ordering is stable hospitality knowledge, not something to rediscover per query at
  inference time.
- **It costs zero model calls and is fully auditable.** Every relaxation writes its
  reason to the state log (`"[refine #1] dropped min_rating"`), which feeds the M4
  governance trail. A ToT expansion would produce a decision no log could reconstruct.

When a fixed policy reaches the same answer as a search, at no model cost, with a
readable audit line, the search is not the more sophisticated engineering choice.

## 5. The reasoning approach that fits

**Grounded ReAct with a bounded refinement loop and human-in-the-loop selection.**

The assignment frames the alternative to ToT as "a linear chain of thought." Worth being
precise: this project uses neither. It is not a single linear chain, because breadth is
real here — it is simply externalized to the guest instead of collapsed inside the model.

Four components, all built:

1. **ReAct-style tool loop** — the model observes, calls a tool, reads the result, and
   decides the next action, bounded at six hops per turn (`_run_turn`,
   `concierge_chat.py:1392`). Reasoning interleaves with real observations rather than
   running ahead of them.
2. **Deterministic state-machine orchestration** — the LangGraph pipeline
   (`parse → search → refine⟲ → match_perks → rank → propose → gate → book → audit`) makes
   control flow inspectable in LangGraph Studio and reproducible in tests.
3. **Bounded backtracking** — the refine loop of §4: one relaxation at a time, capped,
   logged.
4. **Human-in-the-loop selection at every branch point** — shortlist, time, booking
   confirmation, and standing-preference changes. The M4 gate makes the approval explicit
   and recorded.

All of it sits on retrieval: Google Places for candidates, hybrid semantic + metadata RAG
for perks, Tavily with citations for menu highlights. The model's job is to *converse over
grounded facts*, never to imagine a restaurant, a time, or a dish.

### Why this supports the goal better than ToT

| | ToT | This architecture |
|---|---|---|
| Where branches come from | Model generation | Retrieval from real inventory |
| Who evaluates | LLM critic on an invented rubric | The guest, on their own occasion |
| Pruning | Score threshold, silent | Guest declines, visibly |
| Termination | Depth limit or critic satisfaction | Guest says yes; confirmation id returned |
| Auditability | Discarded branches hard to reconstruct | Every step logged for the M4 trail |
| Cost per decision | ~10–25 extra model calls | 0 extra |
| Failure mode | Prunes the restaurant the guest wanted | Guest sees the option and says no |

The agent's goal is not to compute the optimal restaurant. It is to help someone book a
table they are glad about, while remembering them accurately and never acting on their
behalf without asking. Every axis on which ToT is strong — autonomous exploration,
internal evaluation, committing to a single searched-out answer — is an axis on which
this product deliberately does less.

## 6. Risk this decision accepts, and its mitigation

Choosing a fixed relaxation ladder over search accepts one real risk: **the ordering is a
designer's prior, and it can be wrong for a given guest** — someone for whom price is
inviolable and cuisine is flexible gets served in the wrong order.

*Mitigation:* the relaxation is announced, not silent. The concierge tells the guest what
it widened ("nothing vegan-friendly in Midtown under $$ on Friday — I've looked one price
band up, want me to try further out instead?"), which returns the branch decision to the
person holding the real preferences. This costs one conversational turn, no model
overhead, and it is consistent with the same principle that governs the consent gate.

## 7. When to revisit

This is a judgement about this system, not a position on ToT. It should be reopened if
any of the following becomes true:

- **Candidate generation stops being retrieval.** A multi-venue evening — drinks, dinner,
  dessert, with travel time and closing hours interacting — is a genuine combinatorial
  plan the model would have to construct. That is a ToT-shaped problem.
- **A trustworthy evaluator appears.** Enough booking outcomes and post-dining feedback to
  train or ground a scorer would give pruning something real to stand on, extending the
  `perks/eval.py` approach from retrieval to selection.
- **The product moves toward autonomy.** If the agent were ever asked to book without a
  human at the branch points, the search would have to move inside — and then it should be
  a tree, evaluated and logged, rather than a single greedy chain.

Until then, the correct engineering decision is to keep the breadth where the guest can
see it.
